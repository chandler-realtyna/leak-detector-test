Why Your Database Index Isn't Being Used

The index is right there. The column is indexed. The query still does a full table scan. This is the most common support ticket in database engineering, and almost always the cause is one of six things.

An index is a bet the planner is free to decline. Its existence changes what's possible, not what will happen — the planner still has to estimate that using it is cheaper than not, and that estimate is where most surprises live.

Low selectivity

An index on a boolean column, or any column where one value dominates, often isn't worth using even when it exists. If 95% of rows have status = 'active', a query filtering for exactly that value will read almost the whole table either way, and jumping through an index to do it row by row is slower than just scanning the table sequentially. The planner is usually right to skip the index here, and forcing it rarely helps.

Implicit type casts

Comparing an indexed integer column against a string parameter, or an indexed text column against a differently-collated string, can silently disqualify the index, because the planner would need to cast every stored value to compare it — which defeats the point of an ordered structure built on the original type. This is one of the more infuriating cases because the query looks completely correct and returns the right rows; it's simply slow, and the EXPLAIN output has to be read carefully to notice the cast happening at all.

Functions applied to the indexed column

A predicate like WHERE LOWER(email) = 'x' generally cannot use a plain index on email, because the index stores the original values, not the function's output. The fix is usually a functional or expression index built on LOWER(email) directly, or, more simply, normalizing the case at write time so the query never needs the function at all.

Stale statistics

The planner's cost estimates come from statistics about data distribution, gathered periodically, not from the live table. After a large bulk load or delete, those statistics can be badly out of date, and the planner will make confidently wrong choices based on a picture of the table that no longer exists. Running an explicit analyze after a big data change fixes more "the index stopped working" tickets than almost anything else on this list.

The wrong column order in a composite index

An index on (a, b) can serve a query filtering on a alone or on a and b together, but generally cannot efficiently serve a query filtering on b alone — the index is sorted by a first, so b's values are scattered throughout it. Composite index order should follow query patterns, not the order columns happen to appear in a CREATE TABLE statement.

The query really is cheaper as a scan

Sometimes the planner is simply correct. For a query expected to return a large fraction of a small table, a sequential scan can beat an index lookup outright, because reading the whole table in order is one pass, while an index lookup for many rows means many separate, non-sequential reads. Fighting the planner into using an index in this situation usually makes the query slower, not faster — which is the counterintuitive lesson underneath most of this list: the index not being used is frequently the planner doing its job correctly, and the real bug is a mismatch between the query's actual selectivity and what the schema was designed to optimize for.
