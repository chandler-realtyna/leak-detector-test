What Garbage Collectors Actually Throw Away

A garbage collector never finds garbage. It finds the things that aren't garbage, and assumes everything else must be.

That inversion is the whole trick, and it's worth sitting with, because it explains most of the surprising behavior people run into: memory that "should" be freed but isn't, pauses that show up at the worst possible moment, and objects that stick around far longer than their last use would suggest.

Reachability, not usefulness

A collector's job is to compute the set of objects reachable from a set of roots — global variables, stack frames, CPU registers — by following references transitively, and then reclaim everything not in that set. Nothing in this process asks whether an object is still useful. A ten-megabyte cache that nothing will ever read again is perfectly safe from collection as long as one stray reference to it survives somewhere, forgotten, in a closure or a static field. This is the mechanism behind almost every "memory leak" in a garbage-collected language: not a leak in the C sense, but an accidental proof of reachability for something the programmer considers dead.

Tracing versus counting

The two broad families work from opposite ends of the same idea. Reference counting keeps a tally per object and frees it the instant the count hits zero — simple, and useless against cycles, since two objects that only reference each other will never reach zero on their own without a separate cycle detector bolted on. Tracing collectors walk the reachability graph from the roots outward, which handles cycles for free, at the cost of needing to pause the world, or some clever fraction of it, while they do the walking.

Most production runtimes today are generational tracing collectors, built on an empirical observation: the overwhelming majority of objects die young. A generational collector therefore scans the young generation constantly, cheaply, and the old generation rarely, expensively, on the theory that anything that survived several young-generation scans has earned the right to be checked less often.

The pause is a promise, not an accident

Stop-the-world pauses exist because moving or reclaiming an object while another thread holds a reference to its old address is a correctness problem, not a performance one. Modern collectors spend enormous engineering effort shrinking that window — concurrent marking, incremental sweeping, read and write barriers that let mutator threads keep running while bookkeeping happens in the background — but the underlying promise, that no thread ever observes a half-moved object, is non-negotiable, which is why pause times can be reduced but never fully eliminated for collectors that compact memory.

What this means for the code you write

Because collection is about reachability, the practical lever a programmer has is scope: the sooner a reference goes out of scope, the sooner the object it points to becomes eligible. Holding onto a large object "just in case" in a long-lived container is the single most common way to defeat an otherwise well-tuned collector. The collector is not being lazy or wrong in these cases — it is doing exactly what it was designed to do, which is trust the graph, not guess at intent.
