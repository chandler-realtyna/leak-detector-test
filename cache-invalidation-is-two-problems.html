Cache Invalidation Is Actually Two Problems

Everyone quotes the joke about the two hard problems in computer science. Almost no one splits invalidation into the two problems it actually contains.

The first problem is naming: deciding what a piece of cached data represents precisely enough that you can tell, later, whether it still represents the truth. The second problem is staleness: deciding how wrong a value is allowed to be before it stops being useful. These sound like the same problem. They are not, and conflating them is why so many caching bugs survive code review.

The naming half

A cache key is a claim. user:42:profile claims to represent everything about user 42's profile, which is fine until profile gains a field that changes on a different schedule than the rest of the record — a last-seen timestamp, say, updated every request against a key that is otherwise stable for weeks. Now every write to that one field invalidates or re-derives a cache entry that was mostly still correct. The key was named for the wrong granularity.

Getting the naming right usually means keying on the actual dependency graph rather than on the object that feels natural to a human. That is more keys, more bookkeeping, and it is almost always worth it, because the alternative is either over-invalidation (cheap correctness, expensive cache) or under-invalidation (cheap cache, expensive incorrectness).

The staleness half

Even with perfect keys, someone still has to decide how old is too old. A product price can tolerate being thirty seconds stale. An inventory count during a flash sale probably cannot. The interesting part is that this tolerance is a business decision wearing an engineering costume — it should be stated explicitly, per data type, rather than inherited implicitly from whatever TTL someone typed into a config file in 2019 and nobody has revisited since.

Time-to-live is a blunt instrument for this. It expresses "stale after N seconds" but not "stale after this specific upstream event," which is usually the thing you actually care about. Event-driven invalidation solves that at the cost of needing a reliable event bus and the discipline to fire an event for every code path that mutates the underlying data — including the migration script someone runs by hand at 2am.

Where the two halves fight each other

The worst bugs happen when a system has good staleness policy and bad naming, or the reverse. A five-second TTL cannot save you from a key that silently represents two different things depending on which service wrote it last. And a perfectly precise key graph is useless if nothing ever tells it that upstream data changed, so it just serves increasingly wrong answers with total confidence until the TTL eventually expires.

Treat them as two separate design reviews. Name the thing correctly first, independent of any performance goal. Then, separately, decide how wrong it is allowed to be and for how long. Skipping straight to "let's cache this for sixty seconds" without doing the first step is how you end up debugging a support ticket that only reproduces for one customer, at one time of day, on one server.
